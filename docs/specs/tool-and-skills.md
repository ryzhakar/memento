# Tool and skills as one system

Scope: how the memento tool and the plugin in `plugin/` couple. Decisions 1-4 and the `init` part of decision 5 are built (2026-10-16); decision 1's direction and decision 5's `init --adopt` were overruled by the owner on 2026-10-20. The review of 2026-10-16 (recon, gitignored) found these gaps, now closed except `--adopt`.

## Decisions

1. The skills name the tool's verbs, the tool is subservient to the plugin, and the two release as one: where a skill and the tool disagree, the tool changes. Overruled by the owner, 2026-10-20, "the tool is subservient to the plugin, not the other way around", replacing the steward's two-way coupling. Rests on: owner, 2026-10-14, offering the choice between one-way coupling and embracing it for consistent optimisation; the steward chose embracing it, because goal 1 optimises for agents' efficiency, every user of the plugin also runs the tool, and the merge of the two repositories removed the cost of drift. Open to the owner's override.
2. The skills keep the reasoning and the refusals and hand the mechanics to a verb: a step the tool performs reads "run `memento <verb>`" and says why the step exists, not how to compute it. Rests on: the measurement in the events of 2026-10-14 (init and pat-down cost about 1,200 words that `memento patdown` replaces; the clock stamps events, which removed the hand-written stamp errors).
3. The plugin ships a launcher `plugin/bin/memento` that runs the tool at the tag equal to `plugin/.claude-plugin/plugin.json`'s version (`uvx --from git+https://github.com/ryzhakar/memento@v<version> memento`), so plugin and tool never differ in version. Rests on: decision 1; the installed plugin holds only `plugin/`, so the launcher cannot read the tool from beside it.
4. The `SessionStart` hook runs `memento patdown` through the launcher when the project has `CLAUDE.md` and `.claude/memento.yaml`, and prints its output with the reminder. Rests on: decision 3.
5. One schema dialect, by scaffold: a new verb `memento init` writes a project's `.claude/memento.yaml` (all kinds the tool knows, a `project:` block filled from asked values and git facts) and the stub record for every kind, so a fresh project passes `memento check` once its files are committed; the plugin's `setup` skill runs it for the file-writing and keeps the explaining, the owner's questions and the placing of files a project already wrote, and `plugin/config/default.yaml` is generated from the same source so the two never differ. A test runs `init` in a new repository and checks it. A project with a schema in an older shape (product-catalog, gym) moves to the current shape by hand with a written guide; the tool carries no migration command (owner, 2026-10-20, "keep the tool surface for real work, not for migrations"). Rests on: trainer-u3's report (gym's schema is refused with `declares no 'project:' block`, then crashes with `KeyError`); the steward's run on 2026-10-15 of `memento check` in product-catalog-storage-api (`KeyError: 'sections'`) and in a repository holding the shipped default (`declares no 'project:' block`, after the crash fix); the tool hard-codes 21 kinds (memento/schema.py:29-51); the setup in this repository took a hand-copy of the first project's schema (events of 2026-10-14T20:03).
6. Build order (as built, 2026-10-16): the launcher, hook and first skills landed first, then the remaining skills, then `init`; the schema dialect was planned first and the order deviated because the skills' verbs matched the tool already. A release tags plugin and tool together at one version (0.6.0). Rests on: the verb map in the events of 2026-10-14 and the spec review of 2026-10-16.
